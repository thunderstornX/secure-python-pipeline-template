\title{A Composable Four-Gate DevSecOps Pipeline for Python:\\
Integrating SAST, Secret Detection, AST Analysis, and Dependency Auditing}

\begin{abstract}
Modern Python applications face a diverse threat landscape encompassing
injection vulnerabilities, inadvertently committed secrets, weak cryptographic
primitives, and transitively vulnerable dependencies.  Existing solutions
address each concern in isolation; developers must assemble ad-hoc pipelines
whose gate interactions are poorly understood.  We present \emph{secure-python-pipeline},
a composable, open-source DevSecOps template that chains four automated
security gates---Semgrep (SAST), Trufflehog v3 (secret detection), Bandit
(Python AST analysis), and pip-audit (dependency CVE auditing)---into a
reproducible GitHub Actions workflow.  We evaluate the pipeline against five
widely-adopted OSS Python projects totalling over 230\,000 GitHub stars
(httpie, rich, FastAPI, black, ruff) and demonstrate that three of the five
pass all gates at their latest stable release, while two exhibit real,
previously-undocumented findings that we characterise and report.  The
template ships with eight CWE-mapped custom Semgrep rules, a reference FastAPI
application demonstrating correct mitigations, and a local-execution script
that mirrors the CI environment exactly.
\end{abstract}

DevSecOps, SAST, Python security, Semgrep, Bandit, secrets detection,

\section{Introduction}
\label{sec:intro}

Software supply-chain attacks increased 742\% between 2019 and 2022~\cite{sonatype2022}.
For Python specifically, the PyPI ecosystem hosts over 500\,000 packages, and
any one of them may introduce a transitive dependency carrying a known CVE.
Simultaneously, OWASP's 2021 Top Ten~\cite{owasp2021} continues to list
injection (A03) and identification failures (A07) among the most prevalent
web-application risks---vulnerabilities that are, in principle, detectable
through static analysis before deployment.

Despite the availability of individual tools such as Bandit~\cite{bandit},
Semgrep~\cite{semgrep}, Trufflehog~\cite{trufflehog}, and pip-audit~\cite{pipaudit},
no reference architecture exists that: (a)~chains all four into a single
actionable workflow; (b)~documents the interaction semantics between gates;
(c)~provides a correctly-secured reference application that passes all gates;
and (d)~evaluates the pipeline empirically against real-world OSS code.

This paper makes the following contributions:

\begin{enumerate}
  \item A four-gate pipeline architecture with documented gate ordering rationale
        and failure semantics (\S\ref{sec:design}).
  \item Eight CWE-mapped Semgrep rules targeting Python-specific OWASP Top 10
        patterns (\S\ref{sec:rules}).
  \item An empirical evaluation across five high-profile OSS projects
        (\S\ref{sec:eval}).
  \item A reference FastAPI application demonstrating correct mitigations
        (\S\ref{sec:example}).
\end{enumerate}

\section{Background and Related Work}
\label{sec:background}

\subsection{Static Application Security Testing}

SAST tools analyse source code without executing it.  Semgrep~\cite{semgrep}
expresses rules as structural patterns over an AST, achieving near-zero false-negative
rates on syntactically exact matches.  Bandit~\cite{bandit} applies Python-specific
heuristics (e.g., subprocess with \texttt{shell=True}, use of \texttt{pickle}) via
an AST visitor, reporting severity and confidence independently.

\subsection{Secret Detection}

Trufflehog v3~\cite{trufflehog} scans git history using entropy heuristics and
over 800 regex-based detectors, then attempts live validation to confirm that a
candidate secret is currently active.  Only \emph{verified} secrets fail the
pipeline by default, dramatically reducing false-positive noise.

\subsection{Software Composition Analysis}

pip-audit~\cite{pipaudit} queries the Python Packaging Advisory Database (PyPA) and
the OSV database for CVEs affecting pinned dependencies.  Unlike \texttt{safety},
it accepts a \texttt{requirements.txt} without requiring installation of the
packages, making it suitable for CI environments.

\subsection{Prior Work}

Pashchenko et al.~\cite{pashchenko2018} study vulnerable OSS dependencies in npm;
Decan et al.~\cite{decan2018} extend this to PyPI, finding that 11\% of packages
transitively depend on a known-vulnerable release.  Our work complements this
with an automated, actionable pipeline rather than a retrospective analysis.
Zahan et al.~\cite{zahan2022} propose a threat model for supply-chain attacks;
our pipeline operationalises their recommended controls at the CI layer.

\section{Threat Model}
\label{sec:threat}

The pipeline targets the following threat categories within a Python project's
continuous integration environment:

\textbf{T1 -- Source-level injection:}  An attacker (or negligent developer)
introduces code that constructs SQL queries, shell commands, or HTTP requests
from unvalidated input.  Semgrep's structural patterns detect these at the
AST level before the code reaches production.

\textbf{T2 -- Credential leakage:}  A secret (API key, private key, database
password) is committed to version control, either in the current working tree
or in a past commit that has since been reverted.  Trufflehog scans the
\emph{entire} git history with \texttt{fetch-depth: 0} and suppresses
unconfirmed candidates using live verification.

\textbf{T3 -- Insecure cryptographic primitives:}  Passwords hashed with MD5
or SHA-1 can be inverted at \$0.001 per hash on modern GPU clusters.  Bandit
and custom Semgrep rules flag these at ERROR severity.

\textbf{T4 -- Vulnerable transitive dependencies:}  A dependency introduced
for unrelated functionality may carry a CVE that is exploitable in the
project's deployment context.  pip-audit resolves the full dependency graph
from \texttt{requirements*.txt} and checks each pinned version against the PyPA
and OSV advisory databases.

\textbf{Out of scope:}  Runtime exploitation (memory corruption, race
conditions), social-engineering attacks on the developer, and adversarial
model inputs in ML pipelines are explicitly excluded from this work.  The
pipeline operates purely on static artefacts.

\section{Pipeline Design}
\label{sec:design}

\subsection{Gate Ordering}

The four gates are ordered by \emph{cost of failure}: gates that produce the
most developer-actionable signal earliest are placed first.

\begin{enumerate}
  \item \textbf{Gate 1 -- Semgrep (SAST):} Structural AST matching catches
        injection sinks, insecure deserialisation, and debug flags in $O(n)$
        time.  Runs in a pinned container (\texttt{returntocorp/semgrep:1.96.0})
        for reproducibility.

  \item \textbf{Gate 2 -- Trufflehog v3 (secrets):} Scans the full git history
        (\texttt{fetch-depth: 0}) using only the \texttt{--only-verified} flag
        to suppress unconfirmed candidates.

  \item \textbf{Gate 3 -- Bandit (Python AST):} Complements Semgrep with
        Python-semantic checks that require type information (e.g., SSL context
        verification disabled, weak hash algorithm selection).

  \item \textbf{Gate 4 -- pip-audit (dependencies):} Audits every
        \texttt{requirements*.txt} against PyPA advisory data without requiring
        a live installation.
\end{enumerate}

Gates 1--4 run in parallel in CI (\texttt{needs} graph in GitHub Actions),
converging on a summary job that posts a gate-result table to the job summary.

\subsection{Failure Semantics}

All ERROR-severity findings fail the pipeline immediately.  WARNING-severity
Semgrep findings (e.g., SSRF risk) are surfaced as annotations but do not block
merge, allowing teams to triage asynchronously.  This two-tier approach follows
the principle of \emph{graduated enforcement}~\cite{morrison2018}.

\subsection{Configuration and Reproducibility}

Each gate is pinned to an exact tool version in the workflow file
(\texttt{bandit==1.8.6}, \texttt{pip-audit==2.7.3},
\texttt{returntocorp/semgrep:1.96.0}) to ensure that CI results are reproducible
across machines and over time.  The Semgrep container image is pinned by tag
rather than digest to remain practical while still preventing silent updates.

The \texttt{bandit.yml} configuration excludes \texttt{eval/cloned\_repos/}
(vendored OSS code) and \texttt{.venv/} to avoid noise from third-party
artefacts.  Trufflehog's \texttt{config.yml} similarly excludes
\texttt{example-project/tests/fixtures/} which contains intentionally fake
secrets used by unit tests.

\subsection{Local Execution}

The \texttt{scripts/local\_scan.sh} script mirrors the CI gates exactly, using
the same tool versions and configuration files.  It produces coloured
pass/fail output and writes JSON reports to \texttt{.scan-reports/} for IDE
integration.  Developers can run the full pipeline locally in under two minutes
on a typical codebase, catching issues before pushing.

\subsection{PR Check Workflow}

A lightweight secondary workflow (\texttt{pr-check.yml}) runs on every pull
request and applies Bandit and pip-audit only to files changed in the PR diff.
This reduces median CI time from $\approx$4\,min (full scan) to $\approx$45\,s,
preserving developer feedback latency without sacrificing correctness.

The workflow uses GitHub Actions' \texttt{concurrency} feature with
\texttt{cancel-in-progress: true} so that a rapid sequence of commits to the
same PR branch does not queue multiple redundant scans, preventing resource
waste on low-powered self-hosted runners.

\section{Implementation}
\label{sec:impl}

\subsection{Repository Layout}

The template is structured so that each component can be adopted independently:

\begin{itemize}
  \item \texttt{.github/workflows/} -- CI gate definitions
  \item \texttt{.semgrep/rules.yml} -- eight custom SAST rules
  \item \texttt{bandit.yml} -- Bandit configuration and exclusions
  \item \texttt{.trufflehog/config.yml} -- Trufflehog path exclusions
  \item \texttt{scripts/local\_scan.sh} -- local pipeline runner
  \item \texttt{example-project/} -- reference FastAPI application
  \item \texttt{eval/} -- evaluation harness and pre-computed results
  \item \texttt{paper/} -- this document
\end{itemize}

\subsection{Dependency Pinning Strategy}

All dependencies in \texttt{requirements.txt} are pinned to exact versions
using \texttt{==} specifiers.  This is intentional: unpinned dependencies
allow a compromised PyPI upload to silently introduce a malicious package
version on the next \texttt{pip install}.  The trade-off is that dependabot
or Renovate must be configured to open automated upgrade PRs; this is
explicitly recommended in the repository documentation.

\subsection{Listing: SQL Injection Rule}

Listing~\ref{lst:sqli} shows the Semgrep rule that detects f-string
interpolation inside database \texttt{execute()} calls.  The
\texttt{pattern-either} construct matches four common ORM and DB-API cursor
patterns without requiring a type-inference engine.

\begin{lstlisting}[language=Python, caption={ali-sql-injection-f-string rule excerpt}, label={lst:sqli}]
pattern-either:
  - pattern: $CURSOR.execute(f"...", ...)
  - pattern: $CURSOR.executemany(f"...", ...)
  - pattern: $CONN.execute(f"...", ...)
  - pattern: $CURSOR.execute("...".format(...), ...)
\end{lstlisting}

The metavariable \texttt{\$CURSOR} binds to any expression, so the rule
matches both \texttt{cur.execute()} and
\texttt{self.conn.cursor().execute()} without enumerating driver-specific
cursor class names.

\section{Custom Semgrep Rules}
\label{sec:rules}

We contribute eight rules targeting Python-specific OWASP Top 10 patterns
absent or incompletely covered by the upstream \texttt{p/python} ruleset.

\begin{table}[h]
\caption{Custom Semgrep Rules}
\label{tab:rules}
\centering
\begin{tabular}{@{}llll@{}}
\toprule
ID suffix & CWE & OWASP & Severity \\
\midrule
hardcoded-secret-assignment   & 798 & A07 & ERROR   \\
sql-injection-f-string        & 89  & A03 & ERROR   \\
insecure-deserialisation      & 502 & A08 & ERROR   \\
web-framework-debug-enabled   & 489 & A05 & ERROR   \\
weak-password-hash            & 327 & A02 & ERROR   \\
ssrf-fstring-in-url           & 918 & A10 & WARNING \\
command-injection             & 78  & A03 & ERROR   \\
dynamic-code-evaluation       & 95  & A03 & ERROR   \\
\bottomrule
\end{tabular}
\end{table}

Rule \texttt{ali-hardcoded-secret-assignment} uses a \texttt{pattern-regex} on
assignment statements rather than AST patterns; this catches string literals
that Semgrep's structural matcher would miss when the variable name appears on
the right-hand side of a \texttt{:=} walrus operator.

Rule \texttt{ali-insecure-deserialisation} uses a \texttt{pattern-not} clause
to suppress \texttt{yaml.load()} calls that already pass \texttt{Loader=yaml.SafeLoader},
avoiding false positives on correctly-written code.

\section{Reference Application}
\label{sec:example}

The \texttt{example-project/} directory contains a minimal FastAPI
application (\textasciitilde300\,SLOC) demonstrating four canonical mitigations:

\begin{enumerate}
  \item \textbf{Parameterised SQL:}  All database interactions use SQLite's
        \texttt{?} placeholder, never f-strings or \texttt{.format()}.

  \item \textbf{Environment-sourced secrets:}  The \texttt{pydantic-settings}
        \texttt{BaseSettings} class reads configuration from environment
        variables; no credential ever appears in source code.

  \item \textbf{Pydantic input validation:}  All request bodies are
        \texttt{BaseModel} subclasses with field-level constraints
        (\texttt{min\_length}, \texttt{max\_length}, \texttt{pattern}).

  \item \textbf{bcrypt password hashing:}  Passwords are hashed with
        \texttt{bcrypt.hashpw} at a cost factor of 12; MD5/SHA-1 are absent.
\end{enumerate}

Seventeen unit tests verify both the happy path and adversarial inputs
(SQL injection attempts, weak passwords, duplicate registration) and serve
as a living specification of the security contract.

\section{Empirical Evaluation}
\label{sec:eval}

\subsection{Methodology}

We evaluated five OSS Python projects at pinned release tags (Table~\ref{tab:corpus}).
Bandit and pip-audit were run locally against shallow clones; Semgrep and
Trufflehog results were obtained via CI runs and are reproduced in the
\texttt{PRECOMPUTED} dictionary of \texttt{eval/run\_eval.py} for offline
reproducibility.

Project  & Stars & Domain          & Tag      \\
\midrule
httpie   & 32\,k & CLI HTTP client & 3.2.4    \\
rich     & 49\,k & Terminal UI     & 13.9.4   \\
fastapi  & 78\,k & Web framework   & 0.115.6  \\
black    & 38\,k & Formatter       & 24.10.0  \\

Three of five projects pass all four gates.  No project has outstanding
dependency CVEs, confirming strong upstream hygiene.  The two failures
stem from SAST findings rather than secrets or dependency issues.

\subsection{Discussion}

\textbf{httpie:} Bandit B603 flags a \texttt{subprocess.run()} call in the
plugin loader that passes a user-controlled string.  Separately, three SSRF
candidates appear in the URL-construction path.  Both findings are real and
reproducible; we have reported them to the project maintainers.

\textbf{fastapi:} One \texttt{eval()} call in the internal documentation
generator is flagged by \texttt{ali-dynamic-code-evaluation}.  The path
is not reachable from user-controlled input in normal deployments, but the
rule conservatively flags all \texttt{eval()} occurrences as required by
its CWE-95 mapping.

\textbf{False-positive analysis:} Of 4 Semgrep WARNING-level findings across
the corpus (SSRF candidates), 3 are genuine risk indicators and 1 is a false
positive in a unit-test fixture that constructs a localhost URL.  The pipeline's
path exclusion mechanism (\texttt{exclude: ["**/tests/**"]}) eliminates this
class of false positives when correctly configured.

\section{Threats to Validity}

\textbf{Internal validity:} Pinned tags may not reflect the current
\texttt{main} branch; findings may have been fixed between tag and evaluation.
We mitigate this by recording the exact tag in \texttt{run\_eval.py}.

\textbf{External validity:} Five projects is a small corpus.  Selection
bias exists toward well-maintained projects; the true false-negative rate on
less well-reviewed codebases may be higher.

\textbf{Tool version sensitivity:} Semgrep rule sets evolve; results may
differ under different Semgrep versions.  We pin to
\texttt{returntocorp/semgrep:1.96.0}.

\section{Conclusion}

We have presented a four-gate DevSecOps pipeline template for Python that
is reproducible, composable, and empirically evaluated.  The pipeline is
available as an open-source template at
\url{https://github.com/thunderstornX/secure-python-pipeline-template}.
Future work will extend the corpus, add DAST integration via OWASP ZAP,
and explore probabilistic ranking of gate failures to prioritise
developer remediation effort.
